## 6. Django API integration

The existing endpoint is expected to be:

`POST /api/plan/`

Expected request structure:

```json
{
  "origin": "Chicago, Illinois, USA",
  "destination": "Detroit, Michigan, USA",
  "departure_time": "2026-11-15T14:00:00Z",
  "load_weight": 42000,
  "checkpoint_interval": 25
}
```

The response is expected to resemble:

```json
{
  "recommended_route_id": 3,
  "routes": [
    {
      "route_id": 1,
      "distance_miles": 290.21,
      "duration_seconds": 17974,
      "geometry": [
        [-87.6298, 41.8781],
        [-87.5601, 41.5777]
      ],
      "checkpoints": [
        {
          "mile": 25,
          "lat": 41.5777,
          "lon": -87.5601,
          "eta": "2026-11-15T14:25:00+00:00",
          "weather": {
            "forecast_time": "2026-11-15T15:00:00+00:00",
            "wind_mph": 12.5,
            "rain_in_per_hr": 0.12,
            "snow_in_per_hr": 0
          },
          "risk": {
            "wind_risk": "Low",
            "rain_risk": "Moderate",
            "snow_risk": "Low",
            "overall_risk": "Moderate"
          }
        }
      ]
    }
  ],
  "ranking": [],
  "excluded_routes": []
}
```

This is an illustrative response. Inspect the actual backend and adapt your implementation to its real structure.

Create a reusable API layer.

Requirements:

- Centralized API configuration
- Development proxy to Django
- Configurable production backend URL
- Proper loading and error handling
- Request cancellation where appropriate
- Prevention of stale responses overwriting newer results
- Safe handling of non-JSON server errors
- No hardcoded response data in production components

Do not place all API logic in `App.jsx`.

## 8. Route comparison and recommendation

- High miles

- Average risk score
- No Travel miles
- Recommendation status

The backend ranking priority is:

1. Fewest Severe miles
2. Fewest High miles
3. Lowest average risk
4. Shortest travel time

Routes containing No Travel sections are excluded from safe recommendations.

Provide a concise explanation of why the recommended route ranks first.

Use backend-computed rankings rather than creating an inconsistent frontend ranking algorithm.

## 10. Risk-colored road segments

This is a major feature.

Instead of drawing only a uniformly colored route, provide a **Weather Risk View** that colors road segments according to their estimated risk.

The existing backend calculates risk at checkpoints.

Its mileage-classification approach assigns each interval the higher risk of its two endpoint checkpoints.

Use that same documented rule when displaying the corresponding road segments, unless you implement an explicitly coordinated backend improvement.

Requirements:

- Split or style route geometry according to checkpoint mileage positions.
- Match risk segment boundaries to the route's actual geometry as accurately as possible.
- Preserve the backend's distance-scaling convention.
- Avoid treating coordinate array indices as distances.
- Use appropriate risk colors.
- Allow switching between a route-comparison view and a weather-risk view.
- Clearly distinguish estimated segment risk from measured weather at individual checkpoints.
- Provide a legend for the five risk categories.

Prefer clean, efficient GeoJSON layers over large quantities of HTML elements.

## 11. Interactive 0–48-hour weather forecast heatmap

**This is a required assessment feature, not an optional enhancement.**

Create a functional weather-risk visualization along the route corridor with a forecast-time slider.

The user should be able to:

- Move a slider from hour 0 through hour 48.
- See the selected forecast timestamp.
- See weather-risk visualization update along the route corridor.
- Play and pause the forecast animation.
- Step forward and backward through forecast hours.
- Switch between routes.
- Understand the color scale.
- Inspect the conditions at a location for the selected forecast hour.

Important distinction:

The existing `/api/plan/` endpoint calculates checkpoint risk **at the truck's ETA**.

That is not enough to produce a legitimate 48-hour forecast animation.

**Do not fabricate hourly forecasts, repeatedly display the same ETA weather, or interpolate risk values across unrelated hours merely to make the slider look functional.**

Inspect the existing weather service.

If the backend does not expose hourly forecast data needed for the heatmap, implement the smallest maintainable backend extension necessary.

You may create a dedicated endpoint or extend the existing API response, whichever best fits the architecture.

Requirements:

- Use actual Open-Meteo hourly forecasts.
- Retrieve weather at the appropriate geographical sampling points.
- Use the existing wind, rain, snow and truck-load risk rules.
- Reuse the existing risk engine wherever practical.
- Cover the requested 0–48-hour forecast window when available.
- Correctly handle UTC timestamps and forecast boundaries.
- Make the forecast time basis explicit.
- Avoid duplicate rain/showers accounting; verify the Open-Meteo variable definitions.
- Display missing/unavailable forecast periods clearly.
- Avoid excessive requests when sliding between forecast hours.
- Prefer fetching and caching hourly time series once, then changing the displayed hour locally.
- Batch geographical requests where supported and appropriate.
- Use loading and error states rather than fake data.

The visualization should be visually useful: risk-colored corridor segments or a geospatial risk heat overlay aligned with the truck route, with a professional forecast timeline.

Do not substitute a decorative static gradient for the required functional heatmap.
